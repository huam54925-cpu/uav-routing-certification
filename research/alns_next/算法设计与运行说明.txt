后续推进：固定机队 ALNS + 跨路线强化
2026-10-15

一、定位和验收
本实现针对论文问题一的后续改进，不是重新运行三个已完成问题。
主目标为 Case1 固定三架，探索是否突破论文记载的 Tmax=10.3195 h，最终以每条路线不超过9小时验收。
Case3 固定四架仅用于后续迁移检验。
模型严格保留：基地(0,0)、坐标单位0.1 km、速度55 km/h、每次服务5分钟、I/II/III级分别3/2/1次、同物理点不能连续、基地只在首尾。
输入取自 GitHub 提交 f4f6ece1cbc21831512211ff25a6e971e59d860d 的附件1，已转换为 instances.json；其中保存源表SHA256。
没有把论文模型扩展到续航、动态冲突或问题三时间窗。

二、状态与不变量
每个任务副本拥有0起始唯一整数ID，另映射物理点ID。基地隐含于每条路线首尾，不能作为任务插入。
完整状态始终恰有N条非空路线，每个副本恰好一次，相邻物理点不同。
部分破坏状态允许缺少任务或空路线，但只用于修复，不能进入精英档案或输出为解。
删除分隔任务可能生成 A-A 邻接；实现把后一个A也加入待修复集合，递归保持剩余序列合法。实际移除量因此可能超过原计划q。
插入无合法位置，或最终仍有空路线时，回退整轮。绝不创建第N+1条路线。

三、搜索目标与保存口径
计算 T=max(Tk)，V=sum(max(0,Tk-9))，S=sum(Tk)。
搜索评价 F=T+lambda*V+0.001*S；max模式lambda=0.25，violation模式lambda=2。
它是搜索引导函数，不改变验收约束，也不是原问题最优性证明。
分别保存：
  best_makespan：按(T,V,S)字典序保存；
  best_violation：按(V,T,S)字典序保存；
  best_feasible：通过结构约束且T<=9+1e-9的最好T。
两个超时档案可能是不同解；不能把一个解的T和另一个解的V拼成同一结果。
没有可行见证时输出UNKNOWN，不输出INFEASIBLE。

四、破坏—修复
四种破坏：随机任务移除；最长路线任务移除；按飞行距离的空间相关移除；路线连续片段移除。
一般q在任务总数10%至约33%间随机选取。瓶颈和片段算子的实际移除数还受路线长度限制。
两种修复：
  贪心：枚举所有合法路线和插入位置，选插入后全局F最小的任务/位置。
  regret-2：对每个任务求最优和次优合法位置的F，优先插入差值最大的任务；只有一个合法位置时优先处理。
增量时间为 tau(a,u)+tau(u,b)-tau(a,b)+服务时间；不同副本同物理点时按物理点判定邻接合法性。
目前修复枚举全部位置，以正确性为先；之后可以增加候选边缓存，但应保留全位置回退。

五、强化和自适应
每个修复完成的候选执行120次随机邻域尝试，接受严格降低F的有效移动：
  单路线2-opt；跨路线2-opt*（互换两条路线后缀）；长度2或3的Or-opt（允许同路线或跨路线）。
移动后同时检查源路线闭合接缝、目标插入接缝及非空约束。
这是采样强化，不宣称穷尽整个大邻域。
8个破坏/修复组合分别维护权重，选择概率正比于权重。
奖励：更新任一档案8，当前解改善3，退火接受1，其他0.1。
选中组合权重更新 w=max(0.1,0.9*w+0.1*reward)。
模拟退火温度按已用墙钟比例从0.15降到0.005，劣解接受概率exp(-deltaF/temp)。
时间预算会在修复和强化内部检查；单次检查间隔仍存在少量开销。
Cross-exchange、Ejection chain、遗传算法和岛模型尚未实现，避免第一版同时改变过多因素。

六、文件和运行
Python 3标准库即可运行，无需安装ALNS库。
在本目录运行：
  python3 alns_solver.py --case Case1 --fleet 3 --seconds 60 --seed 0 --out case1.json
  python3 validate.py case1.json
  python3 -m unittest -v test_solver.py

从本程序此前输出继续搜索：
  python3 alns_solver.py --case Case1 --fleet 3 --seconds 600 --seed 1 --warm case1.json --out case1_next.json

--focus violation 启用更强超时惩罚。--iterations 可限制迭代数。
每约10秒原子写入 .checkpoint.json，保存当前状态、三个档案、组合统计和改善轨迹。
检查点可作为--warm的输入，但这是从最好T路线重新开始，尚未实现随机数状态、退火状态的精确续跑。
固定种子配合墙钟停止并不保证不同机器得到完全相同的迭代终点；做轨迹复现应固定迭代数并给足时间。
原论文10.3195小时的完整三架路线未在本次找到，不能声称以该解热启动。当前采用独立构造初解。
任务副本ID用于内部状态；物理点可通过instances.json的顺序与visits映射还原。

七、已完成验证
Case1、N=3、seed=0、预算25秒：完成345轮，初始T=11.2069598415，最好T=10.4334671865。
此解三条路线为10.4334671865、10.4274650230、10.4277751286小时，总超时4.2887073382小时。
独立验证器重新从原坐标计算闭合飞行距离和服务时间；任务计数、唯一副本、邻接与汇总一致性通过。
当前仍无九小时可行解，也未突破10.3195小时。不把短测与论文六小时试验作公平性能对比。
3项自动测试覆盖重复点非法邻接、四类破坏与两类修复的任务守恒和强化、验证器拒绝重复任务与伪造时间。
代码是可运行研究原型，尚无多种子长期效果结论。

八、建议六小时正式实验（尚未运行）

  新算法Case3四架迁移1小时：3种子各20分钟。
每次记录机器、核数、代码和输入哈希、种子、墙钟/CPU时间、T、V、可行率、实际迭代数与算子收益。
旧算法当前仅在种子之间检查部分时间限制，应先补内部预算检查或用进程硬时限，并持续保存最好完整状态，才能公平对比。

若均失败，只报告已找到的时间上界和约束放宽候选，不声称最小必要放宽。
例如找到T=10.43的解，只证明将窗口放宽到约10.43可容纳该解，不能证明少于10.43不行。
